# Feature Specification: Kafka 消息队列 + 分块打散存储 + 并发下载 + 一致性哈希容错

**Feature Branch**: `005-scattered-kafka`  
**Created**: 2025-07-22  
**Status**: Draft  
**Input**: User description: "改为统一使用 Kafka；文件分块直接打散上传到不同的实例，不要让网关成为瓶颈；没必要合并文件，直接打散存储即可，用户下载时从多个微服务实例可以并发下载；多实例哈希环/一致性哈希的设计需要考虑实例宕机的容错"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 分块打散上传 (Priority: P1)

用户上传一个大文件时，客户端先通过网关获取文件上传计划（每个分块应该发送到哪个文件服务实例的地址），然后**绕过网关**，直接将各个分块并行上传到对应的文件服务实例。上传完成后通知系统完成文件记录。网关不再是上传的数据瓶颈。

**Why this priority**: 这是本次重构最核心的变更——打散上传绕过网关。没有这个，后续的无合并存储和并发下载都无从谈起。

**Independent Test**: 上传一个多分块文件，验证分块被分散到多个文件服务实例上，网关仅处理元数据请求，不传输文件数据本身。

**Acceptance Scenarios**:

1. **Given** 用户选择了一个需要分块的大文件, **When** 客户端调用 CheckUpload, **Then** 系统返回上传计划，包含每个分块对应的目标文件服务实例地址
2. **Given** 客户端拿到上传计划, **When** 客户端直接向各文件服务实例地址发送分块, **Then** 各实例分别接收并存储属于自己的分块
3. **Given** 所有分块上传完毕, **When** 客户端调用 CompleteUpload, **Then** 系统记录文件元数据且文件立即可用

---

### User Story 2 - 无合并分块存储与并发下载 (Priority: P1)

文件上传后不执行合并操作，分块以原始形式永久存储在各文件服务实例的本地磁盘上。用户下载文件时，客户端获取分块分布信息，从多个实例并行拉取所有分块后在本地拼接为完整文件。

**Why this priority**: 与 P1-上传配套，决定了整个存储模型。取消合并减少了 I/O 和等待时间，并发下载提升了大文件下载速率。

**Independent Test**: 上传一个多分块文件后，请求下载。验证客户端能从多个实例并发获取分块并正确拼接成原始文件。

**Acceptance Scenarios**:

1. **Given** 一个已打散存储的多分块文件, **When** 用户请求下载, **Then** 系统返回每个分块的位置信息（实例地址 + 分块标识）
2. **Given** 客户端拿到分块分布信息, **When** 客户端并行从各实例获取分块, **Then** 拼接后的文件与原始文件完全一致（MD5 校验通过）
3. **Given** 某个分块因纠删码冗余存在多副本, **When** 主副本所在实例不可用, **Then** 系统返回备用实例地址供客户端获取该分块

---

### User Story 3 - Kafka 消息队列替换进程内通道 (Priority: P2)

系统将进程内 goroutine channel 消息队列替换为 Kafka。所有异步任务（冷热存储迁移、缩略图生成等）通过 Kafka Topic 进行发布和消费，实现多实例间任务的可靠分发和消费。

**Why this priority**: Kafka 是基础设施变更，为多实例协作提供可靠的异步通信基础，但不直接影响用户可感知的上传/下载功能。

**Independent Test**: 触发一次冷热迁移事件后，验证事件通过 Kafka 发布，另一个消费者实例正确消费并执行迁移。

**Acceptance Scenarios**:

1. **Given** 本地磁盘用量超过阈值, **When** 系统触发 LRU 淘汰, **Then** 迁移消息被发布到 Kafka Topic
2. **Given** Kafka 中有待消费的迁移消息, **When** 消费者实例读取消息, **Then** 完成文件从本地到 OSS 的迁移并确认消费
3. **Given** Kafka 消费者处理失败, **When** 消息未被确认, **Then** 消息可被其他消费者重新消费（至少一次语义）

---

### User Story 4 - 一致性哈希容错与分块重平衡 (Priority: P2)

当某个文件服务实例宕机或被移除时，系统能检测到实例变化，在上传和下载场景中将受影响的分块路由到其他可用实例。哈希环支持虚拟节点和故障转移，确保局部失败不导致整体服务不可用。

**Why this priority**: 生产环境必须处理实例故障。虽不影响基本功能，但关乎系统可用性和数据可靠性。

**Independent Test**: 在 3 实例部署中，手动停止 1 个实例后发起上传和下载，验证系统正确降级到 2 个实例且已有数据仍可访问。

**Acceptance Scenarios**:

1. **Given** 3 个文件服务实例正常运行, **When** 1 个实例下线, **Then** 哈希环在 15 秒内剔除该实例，新上传请求路由到剩余实例
2. **Given** 某文件的分块分布在已下线的实例上, **When** 用户请求下载, **Then** 系统尝试从纠删码冗余分片或 OSS 冷存储恢复该分块
3. **Given** 已下线的实例重新上线, **When** 系统检测到恢复, **Then** 哈希环重新纳入该实例，后续请求可再次路由到它

---

### Edge Cases

- 上传过程中某个目标实例宕机：客户端收到失败响应后应能从网关获取更新后的上传计划，将失败分块重新路由到健康实例
- 所有文件服务实例不可用：系统返回服务不可用错误，不丢失已上传的分块数据
- 单分块文件（不需要打散）：系统仍走统一的分块流程，只有 1 个分块路由到 1 个实例
- Kafka 集群暂时不可用：文件上传/下载不受影响（Kafka 仅用于异步任务），异步任务暂停直到 Kafka 恢复后重试
- 文件服务实例扩容：新实例加入哈希环后仅影响后续请求，已上传的分块元数据不变，不需要重新分配历史数据
- 秒传（MD5 命中已完成上传）：跳过分块上传，直接复用已有文件记录
- 断点续传：客户端重新调用 CheckUpload 时，系统返回已上传分块列表及原始上传计划，客户端仅重传缺失分块

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供上传计划接口，根据一致性哈希为每个分块分配目标文件服务实例地址
- **FR-002**: 文件服务实例 MUST 在 gRPC 之外暴露 HTTP 分块上传端点，供客户端直连上传
- **FR-003**: 系统 MUST 在网关层提供 JWT Token 签发或传递机制，确保客户端直连文件服务实例时身份得到验证
- **FR-004**: 系统 MUST 永久以分块形式存储文件，不执行分块合并
- **FR-005**: 系统 MUST 在元数据中记录每个分块的存储实例标识和本地路径
- **FR-006**: 系统 MUST 提供下载计划接口，返回文件所有分块的位置信息（实例地址 + 分块标识）
- **FR-007**: 客户端 MUST 支持并行拉取多个分块并在本地拼接还原文件
- **FR-008**: 系统 MUST 将进程内 goroutine channel 消息队列替换为 Kafka
- **FR-009**: 冷热存储迁移任务 MUST 通过 Kafka Topic 发布并由消费者异步消费
- **FR-010**: 一致性哈希环 MUST 支持虚拟节点，在实例增减时最小化分块重新映射范围
- **FR-011**: 系统 MUST 在实例宕机时于 15 秒内从哈希环中剔除该实例
- **FR-012**: 系统 MUST 支持纠删码冗余编码，针对每个分块独立生成校验分片以容忍部分分片丢失
- **FR-013**: 当分块所在实例不可用时，系统 MUST 尝试通过纠删码重建或 OSS 冷存储副本恢复该分块
- **FR-014**: 系统 MUST 保持秒传（MD5 去重）和断点续传功能的正确性
- **FR-015**: 系统 MUST 保持现有的文件管理功能（列表、重命名、删除、移动、回收站、分享、搜索）不受影响

### Key Entities

- **UploadPlan**: 文件上传计划——将文件分块映射到目标文件服务实例，包含每个分块的目标地址和上传 Token
- **ChunkRecord**: 分块存储记录——记录分块在哪个实例、哪个磁盘路径存储，关联文件 MD5 和分块索引
- **FileStore**: 文件存储聚合——关联完整文件与其所有分块记录，跟踪上传状态
- **ErasureShard**: 纠删码分片——针对单个分块生成的校验分片，分布在不同实例上
- **KafkaMessage**: 异步任务消息——冷热迁移和缩略图生成任务的消息载体

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 大文件上传过程中网关的网络吞吐量降低 90% 以上（仅处理元数据，不中转文件数据）
- **SC-002**: 多分块文件的上传速度相比单网关中转提升至少 2 倍（取决于实例数量和网络带宽）
- **SC-003**: 多分块文件的下载速度相比单点下载提升至少 2 倍（并行拉取）
- **SC-004**: 3 实例部署中任意 1 个实例宕机，已有文件仍可正常下载（通过纠删码或 OSS 恢复）
- **SC-005**: 异步任务（冷热迁移）在单消费者故障时不丢失，由其他消费者在 60 秒内接管
- **SC-006**: 现有全部单元测试继续通过，新增功能的测试覆盖率 ≥ 80%
- **SC-007**: 秒传和断点续传功能在新架构下表现与原有架构一致

## Assumptions

- 文件服务实例之间网络互通，且客户端可以直接访问文件服务实例的 HTTP 端口（在容器部署中需要暴露端口）
- Kafka 集群已部署可用（通过 docker-compose 添加 Kafka 服务）
- 客户端（前端浏览器）支持并发 HTTP 请求（现代浏览器均支持）
- 纠删码编码的开销可接受——针对每个分块独立编码，而非整文件编码
- 分块大小沿用现有配置（默认 5MB），不在本特性中修改
- OSS 冷存储迁移仍然保留作为磁盘空间不足时的溢出策略
- 单实例部署（开发环境）时系统可正常降级运行——所有分块路由到唯一实例
- 现有前端直传 OSS 的预签名上传模式保持不变，本特性的"直连上传"仅针对本地磁盘存储模式
